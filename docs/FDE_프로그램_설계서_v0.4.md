# FDE 프로젝트용 프로그램 설계서 v0.4

작성: 2026-09-30 · 상태: 2차 토론용 (GPT 설계안 교차검토 반영)

## v0.4에서 바뀐 것

GPT가 별도로 작성한 설계안(「연구 주제별 정제 DB 구축 이후의 활용과 지속 갱신을 위한 제품 및 운영 설계 v1.0」)을 검토해 다음을 받아들였다. 처리 내역 전체는 **별첨 D**에 있다.

1. **개발과제 계층을 새로 넣었다** — 프로젝트 아래에 연구원의 실제 개발과제를 두고, 관심 노드·구성·제약을 등록한다. 이것이 없으면 "먼저 내밀기"가 추측이 된다. GPT 안의 가장 큰 기여다 (§5.2)
2. **기준선 개념을 넣었다** — 승인된 DB 버전을 고정하고, 갱신은 별도 후보 영역에서 검토한 뒤 새 기준선으로 공개한다. 미검토 데이터가 집계에 섞이지 않는다 (§5.3)
3. **등급을 세 축으로 쪼갰다** — 벤치마킹 가치, 개발방향 관련성, 권리검토 필요도. "A등급" 한 글자로 침해 위험과 기술 우수성을 함께 표현하지 않는다 (§6)
4. **수치는 AI가 만들지 않는다** — 집계는 검증된 계산 함수가 수행하고 실행 번호를 남긴다. AI는 그 수치를 설명만 한다 (§12.2)
5. **카드에 실행조건을 저장하고 재실행할 수 있게 했다** — 당시 결과를 보존하고, 최신 기준선으로 다시 계산하면 새 버전이 된다. **같은 카드의 수치를 몰래 바꾸지 않는다** (§5.1)
6. **1단계를 바꿨다** — 새 프로젝트를 처음부터 만드는 대신, **이미 수행한 IP-R&D의 정제 Excel과 보고서를 가져오는 것**으로 시작한다. 검증이 몇 달 빨라진다 (§13)

받아들이지 않은 것도 있다. 배포 방식을 "계약에 따라 선택"으로 미루는 것은 MVP 범위를 못 정하게 만들므로 **중앙 웹서비스로 확정한 채 유지한다.**

## 0. 이 문서를 읽는 법

확정 설계가 아니라 **다투기 위한 설계**다. 본문은 하나의 안을 끝까지 밀어붙여 적었고, 갈릴 만한 지점은 **별첨 A의 쟁점 15건**으로 뽑았다. 별첨 B에 다음 토론 라운드용 요청문이 있다.

### 이 문서에서 쓰는 낯선 말

| 말 | 뜻 |
|---|---|
| **FDE** | Forward Deployed Engineer. 고객 현장에 가서 함께 문제를 정의하고 도구를 그 현장에 맞게 세팅해 주는 사람. 여기서는 **특허 센스를 가진 컨설턴트** |
| **정제 DB** | 검색·노이즈 제거·기술분류·등급부여까지 끝난, 그 연구그룹 주제에만 맞는 특허 묶음 |
| **기준선** | 컨설턴트가 승인해 고정한 정제 DB의 한 버전. 모든 분석은 어느 기준선에서 나왔는지 기록한다 |
| **개발과제** | 연구원이 실제로 붙들고 있는 문제 하나. 프로젝트 아래에 여러 개 둔다 |
| **카드** | 하나의 질문에 답하는 최소 산출물 조각. 실행조건을 함께 저장해 다시 계산할 수 있다 |
| **분석 실행** | 집계·비교를 한 번 돌린 기록. 실행 번호, 조건, 사용 문헌, 결과 수치가 남는다 |
| **열람 화면 / 제작 화면** | 같은 웹서비스의 두 얼굴. 연구원이 보는 쪽이 열람, FDE가 보는 쪽이 제작 |

## 1. 이 프로그램이 해결하는 문제

### 1.1 지금 무엇이 실패하고 있는가

전형적인 IP-R&D는 이렇게 흐른다.

```
의뢰인 협의 → 기술트리 작성 → 검색식 구성 → 노이즈 필터링
→ 기술분류 → 등급부여 → [정제 DB 완성]
→ 정량분석 그래프 / 벤치마킹 자료 / 핵심특허 분석(비침해·회피설계·무효)
   / 기술흐름 분석 → R&D 방향성 / 공백특허 → 신규 IP 후보 / TRIZ 적용 후보
→ 최종보고
```

문제는 마지막 화살표에 있다. **모든 산출물이 최종보고일 하루에 한꺼번에 도착한다. 그런데 의뢰인이 그 산출물들을 필요로 하는 시점은 그날이 아니다.**

- 벤치마킹 자료는 연구원이 실제로 그 부분을 설계하는 몇 달 뒤에 필요하다.
- 회피설계 검토는 그 구조를 채택하려고 할 때 필요하다.
- 공백 분석은 다음 과제를 기획할 때 필요하다.

그리고 그 시점이 오면 **보고 내용을 이미 잊었다.** 파일은 서버에 있지만, 무엇이 어디 있는지 모르고, 200쪽 안에서 자기 질문에 답하는 3쪽을 찾아내지 못한다. 결국 쓰이지 않는다.

여기에 두 번째 실패가 겹친다. **시간이 지나면 정제 DB 자체가 낡는다.** 신규 공개 특허가 계속 쌓이고, 근거로 삼았던 특허가 소멸·무효·이전되면 그때 내린 결론이 뒤집힌다. 1년 지난 회피설계 결론은 근거가 살아 있는지 아무도 모르는 문서일 뿐이다.

### 1.2 해결 요건

사용자가 제시한 세 가지:

1. **찾을 수 있어야 한다**
2. **물어볼 수 있어야 한다** — 분석한 사람에게 바로 묻듯이
3. **낡지 않아야 한다**

이 설계에서 두 가지를 더한다.

4. **찾기를 기다리지 않아야 한다** — 연구원은 관련 산출물이 있다는 사실 자체를 잊었으므로 검색어를 떠올리지 못한다. **시스템이 그 시점을 감지해 먼저 내밀어야 한다.** 그러려면 연구원이 지금 무엇을 하고 있는지 시스템이 알아야 하고, 그 장치가 **개발과제**다 (§5.2)
5. **결론에 유효기간이 있어야 한다** — 근거가 흔들리면 시스템이 스스로 "이 결론은 재검토가 필요하다"고 말해야 한다. 일회성 보고서와 살아 있는 자산을 가르는 결정적 차이이며, 구독료를 정당화하는 유일한 근거다

## 2. 누가, 언제, 왜 여는가

| 이용자 | 대표 상황 | 여는 이유 |
|---|---|---|
| **출연연 연구원** | 특정 구조를 채택하려는 중 | "이 구조가 남의 특허에 걸리나" |
| **기업 개발자** | 설계 대안을 고르는 중 | "다른 회사는 이 문제를 어떻게 풀었나" |
| **연구기획자** | 신규 과제 기획 중 | "아직 아무도 안 한 자리가 어디인가" |
| **중소기업 대표** | 투자·수주·정부과제 준비 중 | "우리 제품을 어떻게 개선하고 무엇부터 검토하나" |
| **FDE 컨설턴트** | 구축·운영 중 | "어떤 범위와 기준으로 만들고 유지하나" |

같은 정제 DB에서 출발하지만 **원하는 답의 모양이 다르다.** 연구원은 한 건의 특허를 깊게 보고 싶고, 기획자는 전체 지형을 보고 싶고, 대표는 결론 한 줄을 원한다.

**다만 역할이 화면을 결정하지는 않는다.** 무엇을 내밀어야 하는지 결정하는 것은 역할이 아니라 **그 사람의 개발과제**다. 역할은 화면의 복잡도와 기본 질문 예시만 조정한다. (GPT 안에서 받아들인 관점)

### 핵심 이용 장면 다섯 개

설계 판단이 갈릴 때 이 다섯 장면으로 돌아와 판단한다.

1. **(연구원) 채택 직전 점검** — 회로 구조를 정하고 나서 "이거 걸리나" 확인. 답이 하루 뒤에 오면 이미 설계가 진행되어 버린다 → 즉시 1차 답이 나와야 하는 이유
2. **(연구원) 막힌 문제 앞에서** — "남들은 어떻게 풀었나" 탐색. 특허번호를 모르고 특허 용어도 모른다 → 용어사전(§5.4)이 필요한 이유
3. **(기획자) 내년 과제 초안** — 공백 분석과 기술흐름을 다시 꺼내 본다. 1년 전 것이라 낡았을 수 있다 → 기준선 표시와 재실행이 필요한 이유
4. **(연구원) 어느 날 알림** — "3주 전 공개된 특허가 당신 개발과제 '흔들림 억제'에 걸립니다" → 개발과제 단위 알림(§7.5). 이 장면이 구독 유지의 핵심이다
5. **(대표·기획자) 결론 뒤집힘** — "작년에 회피 가능이라고 드린 결론의 근거 특허가 등록되었습니다" → 이 한 건이 연간 구독료를 정당화한다

## 3. 설계 전제 (확정)

| # | 전제 | 설계에 주는 영향 |
|---|---|---|
| 1 | **웹서비스 하나를 우리가 클라우드에서 운영한다** | 프로그램이 하나다. 열람 화면과 제작 화면은 권한으로 갈린다 |
| 2 | **의뢰인 기관은 이 서비스 접속을 허용한다** | 기관 보안 담당이 우리 주소를 열어 준다. 내부망 격리를 전제하지 않는다 |
| 3 | **특허 데이터는 우리 명의로 중앙에서 수집한다** | 한 번 수집해 모든 기관이 함께 쓴다. 대신 약관 확인이 필수다 (§9.2) |
| 4 | **백지에서 새로 설계한다** | 기존 검색엔진·기존 도구를 전제하지 않는다 |
| 5 | **현장 구축은 FDE가 대면으로, 이후 운영은 원격으로** | 초기 4~6주는 현장 밀착, 이후 대면 없음 |

### 3.1 왜 웹서버 방식인가

**갱신 때문이다.** 프로그램을 기관마다 설치하는 방식에서는 분류·등급·카드가 바뀔 때마다 갱신 파일을 만들어 기관마다 보내고 적용 여부를 확인해야 한다. 기관 10곳이면 매주 10번 일어난다. 중앙 서비스에서는 한 번 고치면 끝이다.

**구독 때문이다.** 이 사업은 "프로젝트 납품"이 아니라 "지속 이용"으로 수익 구조를 바꾸는 것이 목표다. 누가 얼마나 쓰는지 우리가 알아야 하고, 그 기록이 우리 쪽에 있어야 한다.

**이용 기록이 곧 우리의 자산이다.** FDE 사업의 진짜 산출물은 "어떤 산출물이 실제로 쓰이는가"라는 지식이다(§8.8). 중앙 서비스가 아니면 모이지 않는다.

GPT 안은 배포 방식을 "계약과 보안 조건에 따라 선택"으로 남겼다. 그 유보가 합리적으로 보이지만, **배포 방식을 정하지 않으면 권한·갱신·이력 설계가 두 갈래로 갈려 MVP 범위를 정할 수 없다.** 확정한 채로 간다. 외부 AI를 허용하지 않는 기관에 대한 축소 동작만 별도로 준비한다(쟁점 6).

### 3.2 이 선택의 대가

- 서버 장애·백업·보안 대응을 우리가 진다. 사무소에 그 일을 맡을 사람이 필요하다
- 기관 데이터(질문 내용, 이용 기록)를 우리 쪽에 두게 된다. 계약서로 정리해야 한다
- 유료 특허 데이터를 우리가 받아 여러 기관에 보여주는 구조이므로 **약관 확인이 이 설계의 전제 조건**이 된다 (§9.2)
- 공공기관 정식 조달 단계에서 클라우드 보안 요건이 걸릴 수 있다 (§10.4)

## 4. 전체 구조

```
              ┌──────────────── 우리가 운영하는 웹서비스 ────────────────┐
              │                                                        │
 공공 데이터 ──→ [수집기]  ──→ [공용 특허 창고]                          │
 (우리 명의)   상시 수집       전 프로젝트 공유                           │
              │                    │                                   │
              │                    ▼                                   │
              │       ┌─────────────────────────────────────┐          │
              │       │ 기관 공간 A                          │  B │ C  │
              │       │  ├ 프로젝트                          │    │    │
              │       │  │   ├ 기술트리(버전)                 │    │    │
              │       │  │   ├ 기준선 n (승인된 DB 버전)       │    │    │
              │       │  │   ├ 개발과제 1,2,3                 │    │    │
              │       │  │   └ 카드·분석실행·질문             │    │    │
              │       │  └ 갱신 후보 영역 (미검토, 집계 제외)   │    │    │
              │       └─────────────────────────────────────┘          │
              │              ▲          ▲                              │
              │   [제작 화면] │          │ [열람 화면]                    │
              └──────────────┼──────────┼──────────────────────────────┘
                             │          │
                        FDE (우리)   연구원 (기관, 브라우저)
                        외부 AI 호출
```

### 4.1 수집기와 공용 특허 창고

공공 데이터를 상시 수집해 공용 창고에 쌓는다. 서지·전문·도면·권리상태. **한 번 받은 특허는 모든 기관 공간이 함께 참조한다.** 여러 기관의 주제가 겹치면 저장이 한 번으로 끝난다. 중앙 방식의 가장 큰 이득이다.

받은 데이터는 후보 영역으로 들어가고, 검토를 거쳐야 기준선에 편입된다(§5.3).

### 4.2 제작 화면 (FDE)

기술트리 작성, 검색식 구성, 노이즈 판정, 분류·등급 확정, 카드 생성, 감독 대기열, 질문 답변, 기준선 공개. 외부 AI를 호출한다. **프로젝트 여러 건을 한 화면에서 관리하고, 감독 대기열은 기관을 가로질러 하나로 합쳐 보여준다.**

### 4.3 열람 화면 (연구원)

브라우저로 접속하는 쪽. 네 개 진입점(§7.1)과 개인 작업공간.

**기관 공간 분리가 이 설계에서 가장 엄격하게 지켜야 할 규칙이다.** 한 기관의 정제 DB·카드·질문·메모가 다른 기관에 보이는 일은 절대 없어야 한다. 출연연 여러 곳이 경쟁 관계일 수 있고, 한 번 섞이면 사업이 끝난다.

- 모든 조회에 기관 식별자가 조건으로 붙는다. **조건이 빠진 조회는 실행조차 되지 않게 만든다**
- 화면에서 감추는 것으로 권한을 구현하지 않는다. DB 조회, 검색 색인, 임시 저장, 파일 접근, AI 도구 호출, 내보내기 **전부에** 같은 권한이 적용된다 (GPT 지적 반영)
- **공용 특허 창고만 공유한다.** 공개된 특허 원문이므로 공유해도 문제가 없다
- 사용자 권한이 바뀌거나 프로젝트가 이동하면 이전 대화와 저장 결과의 접근권한도 다시 확인한다
- 기관별 데이터 내보내기(계약 종료 시)와 완전 삭제 절차를 처음부터 넣는다

### 4.4 접속 경로

기관 보안 담당이 우리 서비스 주소를 열어 주면 된다. 우리가 지킬 것은 이쪽이다.

- 암호화 접속만 허용
- 기관이 요구하면 **그 기관 인터넷 주소 범위에서만 접속 가능하도록** 제한. 이 기능이 있으면 보안 심사가 훨씬 쉬워진다
- 2단계 인증을 선택 가능하게
- 누가 언제 무엇을 열었는지 기록하고, 기관 관리자가 자기 기관 기록을 직접 조회

## 5. 핵심 설계 개념 다섯 가지

### 5.1 카드 — 보고서를 찾아지는 단위로 쪼개되, 다시 계산할 수 있게 한다

200쪽 보고서가 안 쓰이는 이유는 **찾는 단위와 만드는 단위가 다르기 때문**이다. 만드는 쪽은 "핵심특허 분석"이라는 장 단위로 만들고, 찾는 쪽은 "이 구조 걸리나"라는 질문 단위로 찾는다.

그래서 모든 산출물을 **카드**로 쪼갠다. 카드 하나는 **하나의 질문에 답하는 최소 조각**이다.

**카드의 제목은 질문형으로 쓴다.** 이것이 규칙이다. "A사 US1234567 분석"이 아니라 "플라잉 커패시터를 두 개로 나누면 US1234567을 비켜갈 수 있는가"라고 쓴다. 연구원이 나중에 검색할 때 머릿속에 있는 것은 제목이 아니라 질문이기 때문이다.

여기에 **재실행 가능성**을 더한다. GPT 안의 분석 카드 개념을 받아들인 부분이다.

| 항목 | 내용 |
|---|---|
| 질문형 제목 | 이 카드가 답하는 질문 |
| 결론 | 3줄 이내. 단정할 수 없으면 단정하지 않는다 |
| 근거 | 특허번호 + 문단 번호 + 도면 번호. **근거 없는 문장은 카드에 넣지 않는다** |
| **실행조건** | 어떤 조건으로 계산했는지 — 국가, 기간, 집계 단위(문헌/패밀리), 필터, 분류 버전 |
| **기준선 번호** | 어느 기준선에서 나온 결과인지 |
| **분석 실행 번호** | 수치를 낸 계산 기록 (§12.2) |
| 재검토 조건 | 무엇이 바뀌면 결론이 흔들리는지 (§5.5) |
| 검수 상태 | AI 초안 / 변리사 검수 완료 / 검토 불요(단순 조회·집계) |
| 담당 FDE | 누가 책임지는지 |
| 연결 | 기술트리 노드, **개발과제**, 관련 특허, 관련 카드 |
| 열람 이력 | 누가 몇 번 열었는지 (운영 지표용) |

**같은 카드의 수치를 몰래 바꾸지 않는다.** 이것이 규칙이다. 기준선이 올라가면 카드에 "최신 기준선으로 다시 계산하기" 버튼이 생기고, 누르면 **새 버전**이 만들어진다. 당시 결과는 그대로 남아 언제든 다시 볼 수 있다. 무엇이 왜 달라졌는지도 보여준다.

이 규칙이 왜 중요한가. 연구원이 6개월 전 카드를 근거로 설계 결정을 했는데 그 카드의 숫자가 조용히 바뀌어 있으면, 자기 결정의 근거를 되짚을 수 없다. 특허 판단에서 이건 치명적이다.

**만들 카드 종류:**

1. **특허 요약 카드** — 무슨 문제를 어떻게 푸는가, 핵심 구성, 등급 이유
2. **벤치마킹 카드** — 하나의 문제에 여러 특허가 쓴 수단을 묶어 정리. 연구원이 설계할 때 실제로 보는 것
3. **정량 그래프 카드** — 연도별·출원인별·분류별 추세. 그래프 1장 + 읽는 법 3줄 + **원자료 표**
4. **핵심특허 대응표 카드** — 청구항 구성요소를 쪼개 고객 제품 구성과 하나씩 대비
5. **회피설계 카드** — 어느 구성요소를 어떻게 비켜갈 수 있는지, 대안 수단과 대가
6. **무효 가능성 카드** — 선행자료 후보와 대비표
7. **공백 카드** — 분류축 조합의 저밀도 셀 + 왜 비었는지 해석 (§7.7)
8. **기술흐름 카드** — 세부 분류별·출원인별 변화와 전환 사례
9. **발명 후보 카드** — 착안 → 구성 → 근거 → **검증 과제**
10. **권리상태 변화 카드** — 자동 생성

이 목록은 기존 IP-R&D 산출물과 1:1로 대응한다. **산출물의 내용을 바꾸는 것이 아니라 담는 그릇만 바꾸는 것이다.** 내용을 바꾸면 기존 방법론의 정확성을 잃는다.

### 5.2 개발과제 — 무엇을 먼저 내밀지 결정하는 장치

**v0.4에서 새로 넣은 계층이다. GPT 안에서 받아들인 가장 중요한 부분이다.**

§1.2의 4번 요건("찾기를 기다리지 않는다")을 실행하려면 시스템이 **연구원이 지금 무엇을 하고 있는지** 알아야 한다. 기술트리는 기술의 위치를 나타내지만 연구원의 현재 관심사를 나타내지 않는다. 그래서 프로젝트 아래에 **개발과제**를 둔다.

개발과제 하나에 담기는 것:

- 해결하려는 문제 (연구원의 말로)
- 관심 있는 기술트리 노드들
- 관심 구성·부품
- 제약 조건 (원가, 크기, 사용 환경, 기존 설비)
- 의사결정 시점 (언제까지 정해야 하는가)
- 연결된 카드, 문헌, 발명 후보

예를 들어 교체형 가구 프로젝트에 "무공구 상판 교체"와 "흔들림 억제"를 각각 개발과제로 등록한다. 그러면 시스템이 할 수 있는 일이 달라진다.

| 개발과제가 없으면 | 개발과제가 있으면 |
|---|---|
| 신규 특허를 등급으로만 걸러 보낸다 | "당신의 '흔들림 억제' 과제에 걸리는 특허가 공개됐습니다" |
| 첫 화면에 많이 열린 카드를 보여준다 | 지금 붙들고 있는 과제에 연결된 카드를 보여준다 |
| 재검토 알림을 프로젝트 전체에 보낸다 | 그 결론에 의존하던 과제 담당자에게 보낸다 |
| 질문의 배경을 매번 다시 설명해야 한다 | 과제의 제약을 답변이 이어받는다 |

**개발과제를 연구원이 직접 등록하지 않으면 이 장치가 작동하지 않는다.** 그런데 연구원은 귀찮은 입력을 하지 않는다. 그래서 FDE가 킥오프 워크숍에서 개발과제 초안을 함께 만들어 넣어 준다(§8.1). 이후 연구원이 고치는 것은 쉽다. 빈 칸을 채우게 하는 것과 고치게 하는 것은 부담이 다르다. (쟁점 2)

### 5.3 기준선 — 승인된 DB 버전을 고정한다

**v0.4에서 새로 넣었다. GPT 안의 핵심 기여다.**

v0.3에는 "미분류 특허"라는 상태만 있었다. 그런데 그것으로는 부족하다. 정량 그래프의 숫자가 매주 조금씩 달라지면 연구원은 무엇도 인용할 수 없고, 6개월 전 보고 숫자와 지금 화면의 숫자가 다른 이유를 설명할 수 없다.

그래서 이렇게 한다.

```
[수집] 신규 문헌·법적상태 도착
   ↓
[후보 영역]  중복 / 기존 패밀리 추가 / 신규 패밀리 / 수정 정보로 구분
             AI가 관련성·분류·등급 초안 부여
             기존 핵심특허·개발과제와의 관계를 찾아 표시
   ↓        ← 이 영역은 기본 집계에 섞이지 않는다
[FDE 검토]  변경분과 제외 사유 확인
   ↓
[기준선 n+1 공개]  이 시점부터 새 숫자가 나온다
```

지켜야 할 규칙:

- **모든 분석 요청은 기준선 번호를 받는다.** 어느 기준선에서 나온 숫자인지 항상 알 수 있다
- 범위나 분류 기준의 중대한 변경은 **고객 확인 대상**이다. 조용히 바꾸지 않는다
- 재처리가 실패하면 **이전 기준선을 계속 쓰고 실패 범위를 표시한다.** 불완전한 갱신을 완료로 처리하지 않는다
- 같은 입력이 두 번 들어와도 중복 반영되지 않게 문헌 키와 파일 해시로 막는다
- 법적상태 확인이 실패하면 **마지막 확인일을 표시하고 최신이라고 주장하지 않는다**

연구원 화면에는 후보 영역이 **"새로 도착(정리 중) n건"** 으로만 보인다. 검색 결과와 집계에는 섞이지 않는다. 등급 없는 것을 등급 있는 것과 같은 목록에 섞으면 신뢰가 무너진다.

### 5.4 용어사전 — 연구원의 말과 특허의 말을 잇는다

현장에서 검색이 실패하는 가장 큰 이유는 검색 기술이 아니라 **말이 다르기 때문**이다. 연구원은 "플라잉 캡"이라고 하고 특허는 "부유 커패시터", "플로팅 캐패시터", "flying capacitor"라고 쓴다. 연구원이 직접 검색하면 절반을 놓친다.

그래서 **기관 용어 ↔ 특허 용어 ↔ 영문 대응표**를 프로젝트 자산으로 관리한다.

- 초안은 FDE가 현장 워크숍에서 연구원 말을 받아 적어 만든다. **이것이 FDE가 현장에 가야 하는 가장 실질적인 이유다**
- 이후에는 검색 실패 기록에서 자동으로 후보를 뽑는다. 결과가 0건이었던 검색어, 결과를 열어보지 않고 떠난 검색어가 후보다. **중앙 서비스이므로 이 기록이 실시간으로 쌓이고 FDE가 바로 본다**
- 검색, 1차 응답, 자동분류가 모두 이 사전을 참조한다
- 사용자는 제품 언어로도 찾을 수 있어야 한다. "흔들림을 막는 방식", "상판을 쉽게 빼는 방법" 같은 말이 통해야 한다 (GPT 안에서 받아들인 부분)
- **기관 고유 명칭과 FDE의 판단 기록은 다른 기관 프로젝트로 넘어가지 않는다.** 일반 기술용어만 별도 승인을 거쳐 공용 사전으로 올린다 (쟁점 5)

### 5.5 살아 있는 판정 — 결론에 유효기간을 붙인다

모든 판정 카드(4·5·6번)는 **어떤 근거가 흔들리면 결론이 바뀌는지**를 기계가 읽을 수 있는 형태로 함께 저장한다.

예: 회피설계 카드가 "US1234567의 청구항 1에 '단일 커패시터'라는 한정이 있으므로 두 개로 나누면 비켜간다"고 결론했다면:

- US1234567의 계속출원·분할출원이 공개되면 → 재검토
- US1234567의 청구범위가 보정으로 변경되면 → 재검토
- 같은 출원인의 신규 공개 특허가 이 분류에 들어오면 → 확인
- 12개월 경과 → 정기 재검토

수집기가 이 조건들을 상시 감시하다가 걸리면 해당 카드에 **재검토 필요** 표시를 붙이고, **그 결론에 의존하던 개발과제의 담당자에게** 알린다. FDE가 재검토해 카드를 갱신하면 새 버전이 생기고 이력이 남는다.

**중앙 서비스에서는 이 감시가 한 번만 돌면 모든 기관에 적용된다.** 같은 특허를 근거로 쓴 카드가 여러 기관에 있어도 감시는 한 번이다.

**이 기능 하나가 "일회성 보고서"와 "살아 있는 자산"을 가르는 실질적 차이다.**

## 6. 데이터 구조 (주요 항목)

구현 언어·DB 종류는 정하지 않는다. 담아야 할 항목만 적는다. **모든 기관 데이터 항목에는 기관 식별자가 붙는다.**

**기관** — 이름, 계약 기간, 접속 허용 주소 범위, 구독 상태, 관리자 연락처

**프로젝트** — 기관, 연구그룹, 기술주제(제품 또는 좁은 기술), 목적, 제품조건, 계약 기간, 갱신 주기, 담당 FDE

**개발과제** — 프로젝트, 문제 서술, 관심 노드, 관심 구성, 제약, 의사결정 시점, 담당자, 상태

**기술트리 노드** — 프로젝트, 부모, 이름, **정의문**, 검색식, 버전. *기술트리는 바뀐다.* 노드 이름 수정·통합·분리는 새 버전으로 기록하고, 이전 버전으로 만든 카드가 어느 노드에 걸려 있었는지 추적한다

**기준선** — 프로젝트, 번호, 채택 문헌 집합, 분류·등급 버전, 승인자, 승인 시점, 공개 시점

**특허** (공용) — 번호, 국가, 출원인, 발명자, 출원일, 공개일, 등록일, 청구항 전문, 상세설명 전문, 도면 파일, 인용·피인용, 패밀리, **데이터 제공원·확보일·이용 조건**

**권리상태 이벤트** (공용) — 특허, 날짜, 종류(등록·소멸·무효·이전·보정·분할), **관할**, **마지막 확인일**, 출처

**유효특허 판정** — 프로젝트, 특허, 유효/노이즈/미분류/근거부족/재검토필요, 판정 근거, 판정자(AI/사람), 판정일

**분류 배정** — 프로젝트, 특허, 노드, 신뢰도, 제안자, 확정자, 이력. 한 특허가 여러 노드에 걸릴 수 있다

**등급** — 프로젝트, 특허, **세 축으로 분리**:

| 축 | 무엇을 나타내는가 |
|---|---|
| 벤치마킹 가치 | 설계에 참고할 만한 기술 내용이 있는가 |
| 개발방향 관련성 | 이 프로젝트 목적·개발과제에 얼마나 가까운가 |
| 권리검토 필요도 | 침해·회피·무효 검토가 필요한가 |

**"A등급" 한 글자로 침해 위험과 기술 우수성을 함께 표현하지 않는다.** GPT 지적을 받아들인 부분이다. 실무에서 이 혼동이 실제로 사고를 만든다 — 벤치마킹 자료로 좋다는 뜻인지 걸릴 위험이 크다는 뜻인지 구분되지 않기 때문이다. 기존 Excel에 단일 등급만 있으면 원래 값을 보존하고 그 정의를 기록한 뒤 세 축으로 나눠 붙인다.

**분석 실행** — 프로젝트, 기준선, 실행 조건(축·기간·집계 단위·중복 규칙·필터), 사용 문헌 목록, 결과 수치, 도구 버전, 실행 시각, 실행자

**카드** — §5.1의 항목 전체. 분석 실행을 참조한다

**근거** — 카드의 주장, 특허, 원문 위치(문단·청구항·도면), 발췌

**전문 검토 의견** — 대상 문헌, 쟁점, 관할, 대상 청구항, **적용 전제**, 의견, 검토자, 승인 시점

**질문·답변** — 질문자, 개발과제, 질문문, 1차 응답과 성공 여부, FDE 답변, 카드 승격 여부

**용어 항목** — 프로젝트, 기관 용어, 특허 용어 목록, 영문, 출처(워크숍/실패로그), 확정 여부, 공용 승격 여부

**발명 후보** — 프로젝트, 개발과제, 착안, 관련 공백 카드, 차별 구성 초안, 기대 작용 가설, 반례, 추가 조사 과제, 기술검증 과제, 상태

**변경 사건** — 종류, 대상, 발생 시각, 영향받은 카드·개발과제 목록

**알림** — 대상자, 종류, 관련 카드·특허·개발과제, 발송 시각, 열람 여부

**이용 기록** — 누가 무엇을 언제 열었는지, 검색어와 결과 수

**접속·감사 기록** — 접속 시각·주소, 권한 사용 내역, 내보내기 이력

### 6.1 연결이 핵심이다

분석 결과는 실행조건과 기준선에 연결되고, 주장별 근거는 원문 위치에 연결되고, 개발과제는 관심 노드·구성·문헌·카드에 연결된다. 변경 사건이 생기면 **이 연결을 따라 영향받은 카드와 개발과제를 찾는다.** 이 연결이 없으면 §5.5의 알림이 동작하지 않는다.

초기에는 명시적인 연결 표와 규칙으로 시작한다. 관계를 자동으로 추출하는 고도화는 뒤로 미룬다.

### 6.2 덮어쓰지 않는다

원본 문헌과 승인된 결과를 보존한다. 노드 이름 수정, 노드 통합, 분류 변경, 의견 수정은 모두 새 버전으로 기록한다.

**분류 기준이 바뀐 구간이 포함된 시계열 그래프에는 그 사실을 표시한다.** 같은 기준으로 재분류했는지 여부를 밝히지 않고 변경 전후를 이어 붙여 "기술 변화"로 설명하면 안 된다. GPT가 지적한 함정이고, 실제 IP-R&D 보고서에서 흔히 일어난다.

## 7. 열람 화면 기능 상세 (연구원용)

### 7.1 네 개 진입점

검색창만 있는 첫 화면은 실패한다. 연구원은 검색어를 떠올리지 못해서 안 쓰기 때문이다. GPT 안의 진입점 구조를 받아들여 네 개로 나눈다.

| 진입점 | 여기서 하는 일 |
|---|---|
| **물어보기** | 질문 입력, 예시 질문 선택 → 답변·그래프·근거 |
| **찾아보기** | 과거 결과를 주제·용도·기술트리로 탐색 → 카드, 보고서 장표, 특허 |
| **내 개발과제** | 내 문제·관심 구성·제약 등록·수정 → 관련 문헌, 대안, 검토 요청 |
| **새로 달라진 점** | 지난 기준선 이후 변화 → 추가 문헌, 영향받은 카드·과제 |

역할에 따라 기본 진입점이 다르다. 연구원은 "내 개발과제", 기획자는 "찾아보기", 대표는 월 요약 한 장이 첫 화면이다. 화면 어딘가에 **현재 기준선 번호와 기준일**을 항상 표시한다.

### 7.2 물어보기 — 질문과 근거를 함께 보는 화면

중앙에 질문과 답변, 결과 아래에 표·그래프·내려받기. 근거를 누르면 옆 패널에서 원문 문단, 청구항, 도면, 기존 검토 의견을 확인한다.

화면에 항상 보이는 것: 현재 프로젝트, 기준선과 기준일, 집계 단위, 적용된 필터, 검수 상태.

**후속 질문은 직전의 문헌 집합과 조건을 유지한다.** "그중 국내 특허만", "방금 그 구조의 분리 동작을 설명해 주세요" 같은 말이 통해야 한다. 조건을 풀거나 이전 결과로 돌아갈 수 있고, 질문이 새 주제로 넘어가면 **적용 중인 조건을 알리고 새 분석으로 저장한다.** (GPT 안에서 받아들인 부분)

답변에 반드시 들어가는 여섯 가지:

| 항목 | 내용 |
|---|---|
| 결론 | 질문에 대한 직접 답 |
| 결과 | 표·그래프 또는 구성 비교와 관련 문헌 |
| 조건 | 기준선, 기준일, 필터, 집계 단위 |
| 근거 | 문헌번호, 사용 청구항 또는 원문 위치 |
| 상태 | 계산 결과 / 승인된 의견 / 미검토 AI 해석 |
| 다음 행동 | 조건 바꾸기, 저장, 검토 요청, 내려받기 |

### 7.3 찾아보기

기술트리를 펼쳐 노드로 찾는 길과, 검색으로 찾는 길을 함께 둔다. **연구원은 검색어보다 자기 기술 구조를 통해 찾는 편이 빠르다.**

- 용어사전을 자동 적용하고 **무엇으로 넓혀 찾았는지 보여준다.** 이 표시가 연구원에게 특허 용어를 가르친다
- **카드를 특허보다 먼저 보여준다.** 질문형 제목이 검색어와 맞으면 그 카드가 답이다
- 결과 카드에 무엇을 설명하는 자료인지, 왜 관련되는지, 마지막 검토일을 표시한다
- **기존 보고서 장표도 검색 결과로 나온다** (§7.8)
- 후보 영역 문헌은 섞지 않는다
- 결과 0건일 때 빈 화면을 주지 않는다. "범위 밖일 수 있습니다 / 전문가에게 물어보기"로 연결하고, 0건 검색어는 용어사전 후보로 기록한다

### 7.4 카드 열람과 조회 연동 제시

카드 본문 + 근거로 바로 이동 + **관련 카드 자동 제시**. 여기서 §1.2의 4번 요건이 구현된다. **특허 상세를 열면 그 특허를 근거로 쓴 카드가 모두 옆에 붙는다.** 연구원이 "이런 게 있었나"를 몰라도 만나게 된다.

카드에는 **믿을 수 있는 정도가 표시**된다. "변리사 검수 완료", "AI 초안", "단순 집계"를 같은 모양으로 놓으면 신뢰가 무너진다.

기준선이 올라간 카드에는 **"당시 결과 보기 / 최신으로 다시 계산하기"** 가 함께 뜬다(§5.1).

### 7.5 새로 달라진 점 — 건수가 아니라 변화를 전달한다

"신규 특허 37건"은 아무도 읽지 않는다. 알림에 담기는 것은 이 넷이다.

1. 새 문헌과 **중요한 이유**
2. **영향받은 개발과제 또는 카드**
3. 재검토할 질문
4. 필요한 다음 행동

우선순위: 내 개발과제 관련 문헌 → 핵심특허의 확인된 상태 변화 → 이전에 비어 있던 영역의 변화 → 그 밖의 신규 공개.

**결론 뒤집힘 알림**(§5.5)이 가장 높은 우선순위다. 고객이 빈도와 관심 범위를 설정하고, FDE가 요약과 중복 알림을 관리한다. 메일 발송은 기관이 허용할 때만 켜고 기본값은 화면 안 알림이다.

여기에 **일정 연동**을 더한다. 과제의 의사결정 시점이나 기관이 등록한 일정 앞에 관련 카드 묶음을 미리 내민다.

### 7.6 내 개발과제

§5.2의 개발과제를 등록·수정하는 화면. 문제 서술, 관심 구성, 제약, 의사결정 시점. 등록하면 관련 문헌과 카드가 자동으로 붙고, 알림이 이 과제 단위로 온다.

**FDE가 만들어 둔 초안이 이미 들어 있고 연구원은 고치기만 한다.** 빈 칸을 채우게 하면 아무도 쓰지 않는다.

### 7.7 공백과 발명 후보

**공백의 정의를 분명히 한다.** 공백은 "분석 범위 안에서 특정 기술 조합이 적게 관측되는 상태"다. **0건인 칸을 신규 발명 가능 영역이나 등록 가능 영역으로 간주하지 않는다.** 함께 보는 것은 두 축 이상의 조합 건수, 전체 대비 비율, 시기별 변화, 출원인 집중도, 인접 조합이다.

점수를 쓴다면 **추가 검토 우선순위로만** 쓰고, 계산식·임계값·최소 표본·미분류 비율·집계 단위를 저장한다. 축이 독립적이지 않거나 분류 누락이 많으면 점수를 내기 전에 **데이터 보완을 먼저 안내한다.** (GPT 안에서 받아들인 부분)

**발명 후보는 가설까지다.** 특허 자료로 할 수 있는 것은 문헌 근거와 발명 가설 제시까지이고, 성능·제조 가능성·원가·안전성 입증에는 고객의 계산·시험·시제품 결과가 필요하다. 프로그램은 검증 계획과 증거를 관리하고, **실제 시험을 한 것처럼 표시하지 않는다.**

후보 상태: 제안됨 → 추가 조사 중 → 기술검증 중 → 전문 검토 중 → 채택 또는 보류. 각 전환에 조건과 기록이 붙는다.

**우리 사업의 특허자산화 부분과 이어지는 지점**이므로 처음부터 넣는다. 권리 귀속은 계약의 문제이고 프로그램은 기록만 한다.

### 7.8 기존 보고서 가져오기

**v0.4에서 새로 넣었다. GPT 안에서 받아들인 부분이며, §13의 1단계를 바꾼 근거다.**

기존 PPT·Word 보고서를 페이지·장표·문단 단위로 가져와 검색 대상으로 만든다. 각 장표에 그 장표가 쓴 특허 집합, 계산 조건, 검토 의견을 연결한다.

연결 정보를 복원할 수 없는 장표는 **"원자료 연결 미확인"** 으로 표시한다. 검색은 되지만 근거 추적은 안 된다는 뜻이다. FDE가 나중에 보완할 수 있게 둔다.

이 기능의 값은 두 가지다. 이미 수행한 IP-R&D 결과를 되살릴 수 있고, **새 프로젝트를 처음부터 구축하지 않고도 제품을 검증할 수 있다.**

### 7.9 개인 작업공간

북마크, 메모, 내 질문 목록, 내가 본 것. 저장한 질문을 **같은 조건으로 다시 실행**할 수 있다. **개인 메모는 그 기관 공간 안에만 있고 우리 쪽 지표 집계에 내용이 포함되지 않는다.** 계약서에 명시한다.

### 7.10 기관 관리자 화면

이용자 등록과 권한, 접속 기록 조회, 자기 기관 데이터 내보내기, 일정 등록, 알림 정책. **출연연 도입에서 이 화면이 없으면 심사를 통과하지 못한다.**

## 8. 제작 화면 기능 상세 (FDE용)

### 8.1 현장 구축 지원 도구

FDE가 킥오프 워크숍에서 연구원과 함께 쓰는 화면. 웹 방식이므로 현장에서 접속해 바로 입력한다.

- **논의 내용을 그 자리에서 기록한다** — 제품 구성, 해결 문제, 개발 예정 방향, 경쟁사, 관심 국가, 기간, 보유 기술, 제약. 회의에서 나온 **가정과 합의사항**을 남긴다
- 기술트리를 함께 그린다. 노드마다 **정의문**을 받아 적는다. 정의문이 없으면 나중에 분류가 흔들린다
- **개발과제 초안을 함께 등록한다** (§5.2). 이것이 이 도구의 핵심 산출물이다
- 용어를 즉석에서 사전에 넣는다
- 대표 특허 몇 건을 함께 보며 유효·노이즈 판정 기준을 잡는다
- **의뢰인이 앞으로 하게 될 질문을 미리 받아 적는다.** 이것이 카드 생성 우선순위가 된다. 의뢰인은 자기가 뭘 원하는지 모르므로 FDE가 예시 과제와 예시 질문을 제시하며 확정해 간다

### 8.2 검색식과 노이즈 필터링

노드별 검색식 작성과 시험. 결과 건수와 표본을 즉시 보여준다. **검색원, 실행일, 검색식이 함께 기록된다.** 노이즈 판정은 AI가 초안을 내고 FDE가 표본을 확인해 확정하며, **채택·제외 사유가 추적된다.**

**판정 기준을 글로 남긴다.** 사람이 바뀌어도 같은 기준이 적용되어야 하고, 신규 특허에 같은 기준을 계속 적용해야 한다.

확정된 검색식은 수집기가 주간 신규 공개를 걸러내는 조건이 된다. **검색식이 곧 갱신 범위**다.

### 8.3 분류와 등급 — AI 초안, 사람 확정

전수를 사람이 보는 것은 비용상 불가능하고, 전수를 AI에 맡기는 것은 정확성상 불가능하다.

- AI가 전수에 분류와 세 축 등급 초안을 부여하고 **신뢰도를 함께 낸다**
- FDE는 **신뢰도 낮은 것, 등급 높은 것, 개발과제 관련 항목, 분류 미결**을 우선 본다
- 그 밖의 일반 항목은 **표본 점검과 묶음 승인**으로 처리한다. 개별 검토와 묶음 승인을 **구분해 기록한다** (GPT 안에서 받아들인 부분)
- 확정 결과는 다음 AI 판정의 기준 사례로 쓴다
- **신규 분류를 자동 승인하는 것은 평가가 쌓인 뒤 제한적으로만 도입한다**

**분류 미결 큐**를 둔다. 신규 특허가 기존 노드에 안 들어가면 여기 쌓이고, 일정 수 이상 쌓이면 "기술트리에 새 가지가 필요합니다"라는 신호가 된다. 이것은 연구그룹에게 그 자체로 정보다.

FDE의 수정 이력에서 **오류 유형을 모아** 재발하는 문헌이나 노드를 우선 표시한다.

### 8.4 카드 생성기

§5.1의 10종을 생성하는 도구. 공통 규칙:

- **근거 특허의 원문 문단을 인용하지 못하면 생성 실패로 처리한다.** 그럴듯한 문장을 만드는 쪽으로 도망가지 못하게 막는 장치다
- **수치는 생성기가 만들지 않는다.** 검증된 계산 함수를 호출해 받은 값을 그대로 쓰고 분석 실행 번호를 남긴다 (§12.2)
- 원문 발췌와 설명을 **분리해서** 담고, 적용 조건을 함께 적는다
- 생성물은 **AI 초안** 상태로 시작하며 검수 대기열로 간다. 판정 카드는 검수 전에 열람 화면에 나타나지 않는다
- 데이터가 바뀌면 재실행하되 **새 버전**을 만든다

### 8.5 감독 대기열

FDE가 아침에 열어 보는 하나의 목록. **"AI가 실질 작업을 하고 컨설턴트는 관리·감독한다"가 이 화면이다.** 여기가 부실하면 FDE 1인당 감당 그룹 수가 늘지 않고, 그러면 사업이 안 된다.

- 새로 들어온 질문 (기한 표시)
- 검수 대기 카드 — 우선순위: 개발과제 관련 → 권리검토 필요도 높음 → 질문 답변용 → 정기 생성물
- 확정 필요한 분류·등급
- 분류 미결 큐
- 재검토 필요 카드 (§5.5)
- 기준선 공개 대기 (검토 끝난 갱신 묶음)
- 용어사전 확정 대기
- 이상 신호 — 0건 검색 급증, 오답 신고, 수집 실패

**기관을 가로질러 하나로 합쳐 보여준다.** 기관별로 화면을 갈아타야 하면 FDE 1인당 감당 수가 늘지 않는다. 정렬 기준은 개발과제 관련성, 요청 기한, 영향도다.

검토자는 수정·승인·반려·추가 자료 요청을 할 수 있고, **같은 쟁점에 대한 과거 판단을 찾아볼 수 있다.**

### 8.6 질문 답변 작업대

질문 하나를 열면 관련 특허, 관련 카드, 그 질문자의 개발과제, 1차 응답이 왜 실패했는지가 함께 뜬다. FDE는 답을 쓰고 카드로 승격할지 정한다.

### 8.7 기준선 공개 관리

- 후보 영역의 변경분을 검토해 **새 기준선으로 공개**한다 (§5.3)
- 대량 변경(분류 재배정, 등급 기준 변경)은 **한 묶음으로 예약 공개**한다. 연구원 화면이 하루 종일 조금씩 바뀌면 혼란스럽다
- 범위·분류 기준의 중대한 변경은 고객 확인을 거친다
- 잘못 공개한 것을 되돌릴 수 있고 이력이 남는다
- **두 사람이 같은 분류를 동시에 수정하면 충돌을 탐지하고 이전 변경을 덮어쓰지 않는다** (GPT 안에서 받아들인 부분)

### 8.8 운영 지표 — FDE 사업의 진짜 산출물

FDE 사업을 하는 이유는 용역 수익만이 아니라 **현장 경험 축적**이다. 그 경험이 사람 머릿속에만 남으면 솔루션 요구사항으로 바뀌지 않는다. **중앙 서비스이므로 이 지표가 자동으로 모인다.**

| 지표 | 보는 목적 |
|---|---|
| **어떤 카드가 열렸고 어떤 카드가 한 번도 열리지 않았는가** | 다음 프로젝트에서 **안 만들 근거**. 기존 IP-R&D가 관성으로 만들던 산출물을 걷어내는 유일한 증거 |
| 질문 유형 분포 | 자동화할 다음 대상 |
| **AI 초안 수정률과 수정 유형** | 자동화 범위와 분류 규칙 개선 |
| 1차 응답 해결률 추이 | 자동화가 축적되는지 |
| 검토 대기 시간과 건수 | 원격 지원이 병목인지 |
| 질문에서 답변까지 걸린 시간 | 약속 지키는지 |
| **개발과제별 재방문과 저장 결과 활용** | 최종보고 이후 실제로 쓰이는지 |
| 근거 확인·재현 성공률 | 신뢰성 |
| 갱신 성공률과 중요 변화 누락 | DB 실용성 유지 |
| **분석 1건당 비용과 검토 소요 시간** | 운영 원가. 서비스 범위 조정의 근거 |
| FDE 1인당 감당 그룹 수 | 사업 성립 조건 |
| 기관별 주간 활성 이용자 | 구독 해지 위험 조기 감지 |

**기관 데이터를 우리가 보는 범위를 계약서에 명시한다.** 이용 통계와 질문 내용은 서비스 개선 목적으로 보고, 개인 메모는 보지 않고, 다른 기관에 보이지 않는다. **FDE의 판단 기록을 AI 학습이나 다른 고객 프로젝트에 자동 공유하지 않는다.** 범용화할 운영 지식은 비식별화 후 별도 승인해 재사용한다.

### 9.1 해야 할 일

- **정규화** — 번호·날짜·출원인 이름을 한 형식으로. **출원인 이름 통일이 정량분석 정확도를 좌우한다**
- **집계 단위 구분** — 문헌 단위와 패밀리 단위를 반드시 구분해 저장하고, 모든 집계에 어느 단위인지 표시한다. **패밀리가 확인되지 않으면 추정값을 확정값과 구별한다** (GPT 지적 반영)
- **권리상태 상시 감시** — §5.5가 여기 달려 있다. 주간 단위. **관할과 마지막 확인일을 함께 기록한다**
- **도면 확보와 쪼개기** — 카드가 "도 3의 아래쪽 구조"를 근거로 제시해야 하므로 도 단위로 쪼갠다
- **번역** — 일본·중국. 기계번역을 쓰되 원문을 함께 보관하고 근거 인용 시 원문 위치를 표시한다
- **출처와 이용 조건 기록** — 데이터 제공원, 확보일, 원문 위치, 사용·재배포 조건을 문헌마다 남긴다

### 9.2 반드시 확인해야 할 것 — 이 설계의 전제 조건

**중앙 수집 방식에서 가장 먼저 확인할 것은 데이터 제공 약관이다.** 우리가 유료 API로 받은 데이터를 여러 기관 이용자에게 보여주는 것이 허용되는지가 핵심이다.

특허정보진흥센터에 직접 문의해 확정한다.

1. **받은 데이터를 우리 서비스에서 제3자(의뢰인 기관 이용자)에게 열람시켜도 되는지** — 안 되면 설계를 다시 짜야 한다. 가장 중요하다
2. **이용자 수·조회 건수에 따른 요금 구조** — 구독료 산정의 기초
3. **원문·도면 저장 보관이 허용되는 범위와 기간**

막힐 경우의 대비책: (가) 기관마다 자기 명의 계정을 등록하게 하고 우리 서비스가 그 계정으로 조회 (나) 원문 보관 없이 조회 시점에 불러오기 (다) 국내는 기관 계정, 해외 공개 데이터는 우리 중앙 수집. (쟁점 3)

### 9.3 수집 범위 — 전량이 아니라 주제 단위

**프로젝트 주제 범위만큼만 받아 쌓고, 프로젝트가 늘면 그만큼 넓힌다.**

- 한 프로젝트 유효특허 500~2000건이면 전문 텍스트 수백 MB, 도면까지 수 GB
- 프로젝트 10건이면 수십 GB. 서버 저장소로 감당 가능
- 신규 공개 감시는 프로젝트 검색식 범위만
- 권리상태 감시는 창고에 있는 특허만
- **여러 기관의 주제가 겹치면 저장이 한 번으로 끝난다**

**파일럿 설계 목표는 프로젝트당 문헌 1만 건, 동시 이용자 5명, 정제 DB 1개다.** 이것은 측정치가 아니라 구현 시험 조건이다. (GPT 안에서 받아들인 부분)

## 10. 서버를 어디에 어떻게 두는가

우리 사무소에 장비를 두지 않는다. **클라우드에서 가상서버를 빌린다.**

### 10.1 어디서 빌리는가

한국어로 결제하고 전화로 문의할 수 있는 곳을 고른다.

| 단계 | 어디 | 왜 |
|---|---|---|
| **개발·시험** (기관 0~1곳) | 카페24 가상서버호스팅 | 가장 저렴하고 신청이 간단. 리눅스 월 9,000원~55,000원(부가세 포함, 설치비 22,000원 별도) |
| **본 운영** (기관 2~10곳) | 네이버 클라우드 또는 가비아 클라우드 | 한국어 기술지원, 세금계산서, 증설 용이. 4코어·16GB 기준 네이버 월 12만 원대, 가비아 17만 원대 (2025년 3월 비교 기준) |
| **공공 정식 조달** | 네이버 클라우드 공공기관용, 가비아 공공기관 전용 클라우드 | 공공기관 조달 절차에 맞는 별도 상품 (§10.4) |

해외 업체는 더 싸다. AWS Lightsail은 리눅스 2코어·4GB·80GB가 월 24달러, 2코어·8GB·160GB가 월 44달러다. 다만 결제·문의가 영어이고 공공기관 영업에서 데이터 소재지 질문이 나올 수 있다.

**권장: 카페24에서 시작해 기관이 2곳 되면 네이버 클라우드로 옮긴다.** 특정 업체 전용 기능을 쓰지 않으면 옮기는 데 하루면 된다.

### 10.2 어느 정도 사양이 필요한가

초기 1개 기관, 연구원 20명, 문헌 1만 건, 카드 수천 건 기준으로 **2코어·8GB·저장소 160GB**면 충분하다. 무거운 작업(수집·분류·카드 생성·보고서 제작)은 **뒤에서 도는 작업으로 분리해** 야간에 돌린다.

- 저장소가 먼저 부족해진다. 도면 때문이다. 저장소만 따로 늘릴 수 있는 상품을 고른다
- AI 호출은 외부에 맡기므로 서버에 고성능 연산 장치가 필요 없다. **이것이 비용을 크게 낮춘다**
- 기관 10곳쯤에서 4코어·16GB 수준

**응답 목표**: 검색·집계 5초 이내, 설명 생성 30초 이내, 긴 보고서는 뒤에서 도는 작업. 실제 원문 길이와 모델 조건에 따라 측정해 조정한다.

### 10.3 "안정적"은 장비가 아니라 네 가지 습관이다

1. **자동 백업** — 매일 전체 사본, 최근 2주 보관. 월 몇천 원이다. **복구를 실제로 한 번 해 본다.** 해 보지 않은 백업은 백업이 아니다
2. **접속 통로 제한** — 관리용은 사무소 주소에서만, 이용자용은 기관 주소 범위에서만
3. **살아 있는지 감시** — 서비스가 죽으면 문자로 알리는 무료 감시 도구. 기관이 먼저 전화하는 상황을 만들지 않는다
4. **복구 절차를 글로 남긴다** — 무엇을 어떤 순서로. 사람이 한 명일 때 특히 중요하다

여기에 **장애 시 축소 동작**을 더한다. AI 모델이 죽어도 **기존 결과 조회와 집계 계산은 계속 제공하고**, 설명 생성만 실패했다고 알린다. 수집이 실패하면 화면에 표시하고 우리에게 알린다. **낡은 DB를 최신으로 착각하는 것이 이 설계 최대의 위험이다.**

### 10.4 공공 조달 단계

출연연이 정식 구매할 때 클라우드 보안 요건이 걸릴 수 있다. 공공기관이 쓰는 클라우드에 요구되는 인증 제도가 있고 2026년 현재 개편 중이라는 보도가 있다. **조달 방식이 정해지는 시점에 확인하고, 지금 미리 비싼 선택을 할 필요는 없다.**

대비는 설계에서만 한다. **특정 클라우드 전용 기능을 쓰지 않는다.** 그러면 옮겨야 할 때 옮길 수 있다.

### 운영 (21주~, 대면 없음)

- **매주 자동**: 신규 공개 수집 → 후보 영역, AI 분류·등급 초안, 권리상태 변화 감지, 재검토 조건 점검
- **매주 FDE**: 감독 대기열 처리 — 분류·등급 확정, 카드 검수, 질문 답변, **기준선 공개**
- **월간**: 신규 카드 생성, 운영 지표 검토, 기관별 활성 이용자 확인
- **분기**: 기술트리 점검(분류 미결 큐 정리), 등급 기준 재검토, 발명 후보 협의, 표본 재검사
- **연간**: 범위 재협의, 갱신 계약

**원격으로 해결하기 어려운 범위 변경이나 빠진 제품조건은 추가 확인 요청으로 처리한다.** 요청마다 담당자, 접수 상태, 답변 목표 시점, 필요한 자료를 표시한다. **무제한 분석을 전제하지 않고** 검토 대기량과 소요 시간을 FDE가 관리하며, 처리 기한은 계약으로 정한다. (GPT 안에서 받아들인 부분)

과금은 **구축비 + 월 구독**이다. 이용자 수로 과금하면 기관이 계정을 아끼고, 그러면 §14의 첫 지표가 떨어진다. **연구그룹 단위 정액이 이 사업의 목표와 맞는다.** (쟁점 12)

## 12. 품질과 책임

### 12.1 답변을 세 층으로 가른다

v0.3은 "판정 카드는 예외 없이 검수"였다. GPT가 "모든 질문을 사람 승인 대기로 만들지 말라"고 지적했고, 이 지적이 맞다. 대기 상태가 많아지면 연구원이 묻지 않게 되고, 그러면 이 사업의 핵심 가치가 무너진다. 세 층으로 가른다.

| 층 | 무엇 | 처리 |
|---|---|---|
| **즉시** | 승인된 기준선의 조회·집계, 이미 승인된 의견의 설명 | 검수 없이 바로 답한다. "단순 집계"로 표시 |
| **근거 표시** | 새로운 비교, 기술흐름 해석, 벤치마킹 설명 | 바로 답하되 **"미검토 AI 해석"** 으로 표시하고 근거를 함께 제시 |
| **검수 필수** | 비침해·무효·회피설계에 관한 **새로운 판단** | 쟁점과 관련 문헌 초안만 보여주고 전문 검토로 연결. **검수 없이 결론을 내지 않는다. 예외 없다** |

세 번째 층이 변리사법 경계다. 우리는 변리사 사무소이므로 제공 자체는 문제되지 않지만, **AI가 만든 초안이 검수 없이 결론으로 도달하는 경로**를 구조로 막아야 한다.

### 12.2 수치는 AI가 만들지 않는다

**v0.4에서 새로 넣은 규칙이다. GPT 안의 중요한 기여다.**

집계와 비교는 **검증된 계산 함수**가 수행하고 분석 실행 번호를 남긴다. AI는 그 결과를 설명만 한다. **AI가 수치를 직접 쓰거나 계산하지 않는다.**

- AI에게 임의 코드 실행이나 제약 없는 DB 질의 권한을 주지 않는다. 허용된 도구와 정해진 매개변수로만 실행한다
- 같은 조건의 수치는 **재현되어야 한다.** 설명 문장이 매번 똑같을 필요는 없다
- **인용한 문헌과 문단이 실제 검색 근거에 포함되어 있는지 서버가 확인한다.** 없는 근거를 인용하면 답변을 내보내지 않는다
- 문헌에 없는 구성이나 청구항 내용을 보완해 만들어내지 않는다
- 근거가 서로 충돌하면 어느 자료가 왜 다른지 제시한다
- 고객 제품조건이나 법적상태가 확인되지 않으면 **적용 가능한 범위를 답변에 명시한다**
- **파일 안의 지시문은 데이터로 취급한다.** 문서에 적힌 문장이 권한이나 실행 정책을 바꾸지 못하게 한다

### 12.3 표시 규칙

- 카드는 **참고자료**이며 정식 감정·의견서와 다르다는 점을 열람 화면에 적는다
- 근거 없는 문장은 넣지 않는다
- 단정할 수 없는 것은 단정하지 않는다. "비침해"가 아니라 "이 한정 때문에 비켜갈 여지가 있다"
- **기준선 번호와 기준일을 항상 표시한다**
- 법적상태는 **관할과 마지막 확인일**을 함께 적고 최신이라고 주장하지 않는다
- 추정값과 확정값을 구별한다

### 12.4 기관 데이터에 대한 책임

계약서에 이 다섯 가지를 적는다.

1. 기관 데이터는 그 기관 공간에만 있고 다른 기관에 보이지 않는다
2. 우리가 보는 범위는 이용 통계와 질문 내용까지이며, 개인 메모는 보지 않는다
3. **FDE의 판단 기록을 다른 고객 프로젝트나 AI 학습에 자동 공유하지 않는다.** 범용 운영 지식은 비식별화 후 별도 승인해 재사용한다
4. 계약 종료 시 기관 데이터를 내보내 주고, 요청하면 완전 삭제하고 서면으로 확인한다
5. 접속 기록을 기관 관리자가 직접 조회할 수 있다

고객이 제공한 제품자료·도면·개발 계획은 **특허 공보와 별도 접근권한**을 적용한다.

### 12.5 실패와 한도

- 작업마다 상태를 대기·실행·성공·부분 실패·실패로 관리한다. **일부 파일 실패가 전체 성공으로 보이지 않게 한다**
- 재시도에 중복 방지 키를 쓴다
- 이용자별 요청 한도, 프로젝트별 비용 한도, 긴 작업 취소 기능을 둔다
- 기밀 자료를 불필요하게 기록이나 외부 모델에 보내지 않는다

### 12.6 정확성 관리

- 표본 재검사: 분기마다 확정된 분류·등급에서 표본을 뽑아 다시 본다. 어긋난 비율을 기록한다
- 오답 신고 버튼: 연구원이 누르면 감독 대기열로 간다
- 동일 질문 이중 답변 비교: 같은 질문에 다른 FDE가 다른 답을 내는지 주기적으로 점검

## 13. 만들 순서

**v0.4에서 1단계를 바꿨다.** v0.3은 새 프로젝트를 처음부터 구축하는 것이 1단계였다. 그러면 검증까지 20주가 걸리고, 그 20주 동안 "연구원이 열어 보는가"라는 가장 중요한 질문에 답을 얻지 못한다.

**이미 수행한 IP-R&D의 정제 Excel과 보고서를 가져오는 것으로 시작한다.** 자료가 이미 있으므로 몇 주 안에 실물을 띄울 수 있고, 그 기관의 연구원이 실제로 열어 보는지 바로 확인된다. GPT 안에서 받아들인 부분이며, 이 문서에서 가장 실질적인 개선이다.

### 1단계 (0~4개월) — 기존 자료로 실증

목표: **연구원이 열어 보는가**를 확인한다.

- 서버 마련(카페24 수준), 접속·권한·**기관 공간 분리**, 접속 기록
- **가져오기**: 정제 Excel(열 매핑, 원본 행 추적, 품질 검사), 기존 PPT·Word 보고서(장표·문단 단위), 특허 원문. 초기 컨설팅의 기술트리·검색식·제외 사유도 함께 등록
- **기준선 1 승인 절차** — MVP에서도 생략하지 않는다
- 열람 화면: 네 진입점, 찾아보기(용어사전 적용), 카드 열람, 근거 패널, 물어보기(집계·조회 수준), 개발과제 등록, 저장
- 제작 화면: 카드 수동 작성, 검수, 기준선 공개, 감독 대기열 기본형
- 검증된 계산 함수로 집계. **대표 질의 30건의 정답표를 손으로 만들어 대조한다**
- 수집기: 한국 데이터, 주간 신규 공개와 권리상태 변화 → 후보 영역

카드 생성은 **사람이 손으로 한다.** 자동화는 아직 하지 않는다.

기관 공간 분리는 기관이 한 곳일 때 필요 없어 보이지만 **1단계에 넣는다.** 나중에 넣으면 전부 뜯어야 한다.

### 2단계 (4~10개월) — 감독 가능한 운영

- 갱신: 변경분 비교·검토·기준선 공개·재실행, **영향 알림**
- 분류·등급 AI 초안 + 신뢰도, 묶음 승인
- 카드 생성기 5종(1·2·3·7·8번)
- 재검토 조건과 결론 뒤집힘 알림
- 용어사전 자동 후보 추출
- 운영 지표
- 백업·감시·복구 절차 정비 (§10.3)

### 3단계 (10~18개월) — 초기 구축 자동화와 규모화

- 수집기 확장(미국·유럽), 검색원 직접 연결
- 기술트리·검색식 작성 지원, 노이즈 제거 자동화
- 판정 카드 생성기(4·5·6번) + 검수 게이트
- 발명 후보 카드 생성기(9번, TRIZ 적용)와 검증 이력
- 여러 기관 동시 운영, 구독 관리

### 뒤로 미루는 것

외부 특허 DB 완전 자동 수집, 광범위한 문자 인식, 모든 산업 공통 기술트리, 자동 권리 판단, 실제 성능 검증은 초기 범위에 넣지 않는다.

## 14. 판정 기준

두 층위를 구분한다. **인수 시험**은 만든 것이 제대로 동작하는지, **사업 지표**는 이 사업이 되는지를 본다. GPT 안은 앞쪽에 강하고 v0.3은 뒤쪽에 강했으므로 둘 다 싣는다.

### 14.1 인수 시험 (1단계 파일럿 통과 기준)

| 시험 | 통과 기준 |
|---|---|
| 집계 정확성 | 대표 질의 30건의 수치와 포함 문헌이 독립 계산과 일치 |
| 원문 추적 | 표본 30문헌의 파일·청구항·페이지 연결 오류 0건 |
| 후속 질문 | 범위 변경과 필터 유지 시나리오 10건 모두 통과 |
| **기관 격리** | 서로 다른 기관의 검색·파일·임시 저장 유출 **0건** |
| 갱신 재현 | 같은 입력의 중복 반영 0건, 이전 기준선 결과 재현 |
| 검수 통제 | 미검토 판단이 승인 의견으로 표시되는 사례 **0건** |
| 실패 복구 | 부분 적재 실패와 모델 장애 이후 기준선 유지 |
| 사용자 경험 | 대표 이용자 5명이 도움 없이 자료 찾기와 질문 과제를 수행 |

### 14.2 사업 지표

| 무엇 | 기준 | 왜 이것인가 |
|---|---|---|
| 구축 완료 후 **4주·12주** 시점 재방문율 | 연구그룹 인원의 40% 이상 | **가장 중요한 지표.** 기존 보고서는 사실상 0 |
| 카드 열람 중 "구축 당시 만든 카드"가 아닌 비율 | 6개월 후 30% 이상 | 질문에서 새 카드가 자라고 있다는 증거 |
| 개발과제에 연결된 카드 비율 | 50% 이상 | 카드가 실제 문제에 붙어 있는지 |
| 질문에서 답변까지 중위 시간 | 1 영업일 이내 | "바로 물어보듯이"의 실질 |
| 1차 응답 해결률 | 12개월 시점 50% 이상 | 자동화가 축적되는지 |
| 데이터 갱신 성공률 | 99% 이상 | 갱신이 멈추면 설계 전체가 무너진다 |

# 별첨 A. 다음 토론 라운드의 쟁점 15건

**※ 이미 결정된 사항 (다시 다투지 않는다)**
① 배포형이 아니라 **중앙 웹서비스** 방식으로 간다 (§3.1). ② 산출물은 **질문형 제목의 카드**로 쪼갠다. ③ **기준선**을 고정하고 갱신은 검토 후 새 기준선으로 공개한다. ④ **수치는 검증된 계산 함수만** 낸다. ⑤ 등급은 **세 축**으로 나눈다.

**쟁점 1. 서버 운영 부담을 어떻게 감당하는가**
사무소에 서버 운영 경험이 있는 사람이 없다. 선택지: (가) 관리형 서비스를 최대한 쓴다(DB·백업·감시를 상품으로) — 비용이 오르지만 사람이 덜 든다 (나) 직접 구성하고 절차서로 관리 (다) 외부 운영 대행. 기관 10곳 시점의 월 비용과 사고 시 복구 시간을 함께 따진다.

**쟁점 2. 개발과제를 누가 어떻게 등록하게 하는가**
개발과제가 없으면 이 설계의 핵심 장치가 죽는다(§5.2). 그런데 연구원은 입력을 안 한다. 선택지: (가) FDE가 워크숍에서 초안 작성, 연구원이 수정 (나) 질문 이력에서 시스템이 과제를 추정해 제안 (다) 기관 과제관리 자료를 가져와 자동 생성. 각 방법의 정확도와 부담을 따진다.

**쟁점 3. 유료 특허 데이터를 중앙에서 제3자에게 열람시킬 수 있는가**
§9.2의 1번이 막히면 설계가 바뀐다. 선택지: (가) 기관마다 자기 명의 계정 등록 (나) 원문 보관 없이 조회 시점에 불러오기 — 속도와 근거 인용이 어려워진다 (다) 국내는 기관 계정, 해외 공개 데이터는 중앙 수집.

**쟁점 4. 기관 공간 분리를 어떤 방식으로 하는가**
선택지: (가) 하나의 DB에서 기관 식별자로 구분 — 단순하고 저장이 효율적이나 실수 하나로 섞인다 (나) 기관마다 별도 DB — 섞일 위험이 구조적으로 없으나 운영이 무겁고 공용 창고 연결이 복잡하다 (다) 하나의 DB + 접근 제어를 DB 차원에서 강제. 출연연 보안 심사에서 어느 답이 통할지도 함께 본다.

**쟁점 5. 기관 간 지식을 재사용할 것인가**
같은 기술 분야의 용어사전·노이즈 기준·분류 체계를 다른 프로젝트에 참고로 쓰면 구축이 빨라진다. 그런데 기관은 "우리 돈으로 만든 것을 남에게 쓰는가"라고 묻는다. 이 문서는 (나)를 택했다. 선택지: (가) 전면 금지 (나) 일반 기술용어만 비식별화·승인 후 공용 승격 (다) 계약서에 명시하고 폭넓게 재사용. **이 답이 FDE 1인당 감당 그룹 수를 크게 좌우한다.**

**쟁점 6. 외부 AI를 허용하지 않는 기관을 어떻게 받는가**
기관이 외부 AI 사용을 금지하면 설명 생성이 불가능해진다. 선택지: (가) 그 기관은 대상에서 제외 (나) 검색·집계 중심 축소 모드 제공 — 기능 차이를 사전에 알린다 (다) 기관 전용 환경에 자체 모델 설치. 축소 모드의 품질 차이를 미리 평가해야 한다.

**쟁점 7. 답변 3층 구분의 경계가 맞는가**
§12.1에서 즉시 / 근거 표시 / 검수 필수로 갈랐다. "새로운 비교와 기술흐름 해석"을 미검토 상태로 바로 보여주는 것이 맞는가. 연구원이 "미검토"라는 표시를 실제로 구별해 읽을 것인가. 선택지: (가) 3층 유지 (나) 기술흐름 해석도 검수 필수로 (다) 미검토는 표시가 아니라 별도 영역으로 분리.

**쟁점 8. 등급 세 축으로 나누면 FDE 부하가 늘지 않는가**
축이 셋이면 판정도 셋이다. 등급 A 후보 전수 확인이 세 배가 될 수 있다. 선택지: (가) 세 축 전부 사람 확정 (나) 권리검토 필요도만 사람, 나머지는 AI + 표본 (다) 처음엔 두 축(벤치마킹 가치, 권리검토 필요도)으로 시작.

**쟁점 9. 1차 응답 해결률을 어디까지 올릴 수 있는가**
12개월 50%를 적었으나 근거가 약하다. 특허 질문은 개별 사정이 커서 재사용이 어려울 수 있다. 낮게 잡으면 FDE 부하가 커지고 사업성이 흔들린다. 두 AI가 각자 추정하고 근거를 댄다.

**쟁점 10. 분류·등급을 AI에 얼마나 맡기는가**
경계를 어디에 두는가가 비용과 정확성을 동시에 결정한다. 선택지: (가) 등급 높은 것만 사람 (나) 상위 30% 사람 (다) 신뢰도 기준선으로만 자동 분기. 묶음 승인의 허용 범위도 함께 정한다.

**쟁점 11. 첫 고객을 출연연으로 잡는 것이 맞는가**
IP-R&D 수요가 가장 높지만 조달이 길고 보안 요구가 강하고 단가 협상이 어렵다. 중앙 서비스 방식에서는 기관 밖에 데이터를 두는 것에 대한 저항도 예상된다. 선택지: (가) 출연연 우선 (나) 중견기업 연구소 우선 (다) 출연연 1곳 + 기업 2곳 동시.

**쟁점 12. 구독료를 무엇에 매기는가**
이용자 수로 매기면 기관이 계정을 아끼고, 그러면 §14.2의 첫 지표가 떨어진다. 연구그룹 정액은 이용을 늘리지만 큰 기관에서 수익을 덜 가져온다. 선택지: (가) 연구그룹 정액 (나) 이용자 수 (다) 정액 + 이용자 구간. **과금 방식이 제품 설계로 되돌아온다는 점이 핵심이다.**

**쟁점 13. FDE 1인이 몇 그룹을 감당해야 사업이 되는가**
5개를 적었으나 근거가 약하다. 이 숫자가 감독 대기열의 자동화 목표를 정한다. 두 AI가 각자 계산하고 전제를 밝힌다.

**쟁점 14. 공백 카드와 발명 후보를 의뢰인에게 어디까지 주는가**
공백은 우리의 특허 자산화 기회이기도 하다. 그대로 주면 의뢰인이 단독 출원하고, 안 주면 계약 범위 문제가 생긴다. 선택지: (가) 전부 제공 (나) 제공하되 공동출원 우선협상권을 계약에 (다) 공백은 제공하고 발명 후보 구성은 별도 계약.

**쟁점 15. 1단계를 기존 자료 가져오기로 시작하는 것이 맞는가**
이 문서는 그렇게 바꿨다(§13). 반론: 기존 보고서는 근거 연결이 끊겨 있어 "원자료 연결 미확인"이 대량으로 생기고, 그러면 제품의 핵심 가치(근거 추적)를 검증하지 못한 채 "열어 보는가"만 확인하게 된다. 선택지: (가) 기존 자료로 시작 (나) 새 프로젝트로 시작 (다) 기존 자료를 넣되 일부 구간만 근거 연결을 복원해 검증.

배경은 이렇습니다. 저는 변리사이고 IP-R&D 용역을 해 왔습니다. 문제는 최종보고일에 모든 산출물을 한꺼번에 주는데 의뢰인이 그 시점에는 각 산출물을 필요로 하지 않고, 정작 필요해지는 몇 달 뒤에는 보고 내용을 잊어버려 활용하지 못한다는 것입니다. 이를 해결하려고 FDE(현장에 나가는 컨설턴트) 방식의 사업을 구상했고, 이 설계서는 그 사업에 쓸 프로그램의 설계안입니다.

**이미 결정된 사항이 다섯 가지 있습니다.** ① 기관마다 프로그램을 설치하는 방식이 아니라 우리가 클라우드에서 운영하는 중앙 웹서비스로 갑니다. 갱신을 한 번에 반영할 수 있고 구독 과금과 이용 지표 수집이 되기 때문입니다. ② 산출물은 질문형 제목의 카드로 쪼갭니다. ③ 승인된 DB 버전(기준선)을 고정하고 갱신은 검토 후 새 기준선으로 공개합니다. ④ 수치는 검증된 계산 함수만 내고 AI는 설명만 합니다. ⑤ 등급은 벤치마킹 가치·개발방향 관련성·권리검토 필요도 세 축으로 나눕니다. 이 다섯 가지를 되돌리는 의견은 필요하지 않습니다.

다음 네 가지를 해 주세요.

**첫째,** 별첨 A의 쟁점 15건을 보고 쟁점마다 어느 선택지를 택할지 정하고 이유를 적어 주세요. 판단을 유보하지 말고 하나를 골라 주세요. 근거가 부족한 쟁점은 "무엇을 확인해야 결정할 수 있는지"를 적어 주세요. 특히 쟁점 2(개발과제를 누가 등록하는가), 쟁점 4(기관 데이터를 어떻게 갈라 두는가), 쟁점 15(1단계를 기존 자료로 시작하는가)를 자세히 봐 주세요.

**둘째,** 이 설계에서 틀렸다고 보는 부분을 지적해 주세요. 특히 다음 네 가지 상황이 이 설계에서 제대로 처리되는지 따져 주세요. ① DB 갱신으로 기존 결과의 숫자가 달라지는 경우 ② 고객 질문이 전문 판단으로 넘어가는 경우 ③ 기술트리가 변경되는 경우 ④ 다른 기관의 데이터가 검색되는 오류가 생길 수 있는 경로.

**셋째,** 이 설계가 **기능이 너무 많아진 것은 아닌지** 봐 주세요. 1단계에서 빼야 할 것이 있으면 무엇을 왜 빼야 하는지 적어 주세요. 기능을 늘리는 제안보다 **연구원의 문제 해결과 컨설턴트 검토 업무량 감소**를 우선해 주세요.

**넷째,** 설계서에 없지만 반드시 있어야 한다고 보는 기능만 제안해 주세요. 제안할 때 그 기능이 어떤 이용 장면에서 쓰이는지 함께 적어 주세요.

답변은 한국어로 써 주시고, 영어에서 온 용어나 전문용어를 쓰실 때는 그 자리에서 뜻을 함께 적어 주세요. 그리고 **권장하는 것과 실제로 확인된 것을 구분해서** 적어 주세요. 근거 없는 단정보다 "이 부분은 확인이 필요하다"고 적어 주시는 편이 저에게 더 유용합니다.

### v0.3에서 지킨 것 (GPT 안에 없거나 약했던 것)

- **카드 제목을 질문형으로 쓴다는 규칙** — GPT의 분석 카드는 재현성에 강하지만 "어떻게 찾아지는가"를 다루지 않았다. §1.1 문제에 직결되는 것은 제목이다
- **조회 연동 제시** — 특허를 열면 그 특허를 근거로 쓴 카드가 붙는다(§7.4). GPT에는 "새로 달라진 점" 진입점은 있으나 조회 시점에 끼워 넣는 장치가 없다
- **용어사전을 프로젝트 자산으로 관리하고 검색 실패 로그에서 후보 추출** — GPT는 한 줄 언급이었다. 이것이 FDE가 현장에 가야 하는 이유를 설명한다(§5.4)
- **"열리지 않은 카드 비율"을 안 만들 근거로 쓴다** — 기존 IP-R&D가 관성으로 만들던 산출물을 걷어내는 논리(§8.8)
- **사업 판정 기준** — 구독 유지율, FDE 1인당 그룹 수, 결론 뒤집힘이 실제 대응으로 이어진 건수(§14.2). GPT는 인수 시험에 강하고 사업 판정에 약했다
- **한국 클라우드 선택과 비용 감각** (§10)
